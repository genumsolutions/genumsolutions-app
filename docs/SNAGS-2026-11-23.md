## S-01 — OLED goes blank on the last two rows once a method connects

> "before doing a conection the cars oled shows the both method connection
> details in the last two line which is good. but when and after the car gets
> connected, it should only display about the connected method only and stop
> blinking. But currently show blank on the last two line which should be
> rectified."

**Status:** `FIXED` (device verification pending) · **Phase 1** · both cars

**Reading.** Idle: rows 3–4 alternate Wi-Fi / Bluetooth frames ("blinking") —
correct. Connected: the owner expects ONE static frame for the connected method
only. Actual: both rows are blank.

**Evidence.** `Oled_1_3.cpp` `redrawNow()`:

```cpp
// U-107c: when one connection is active (exclusive mode), hide connection-method
// rows entirely. Only render when both transports are available (idle).
if (!exclusiveMode) { …draw line3/line4… }
```

`ModeManager::pushExclusiveMode()` sets `exclusive = anyConnected && wifiEnabled
&& btEnabled`, so the normal "client connected, both transports on" case hides
the rows by design. `Oled_1_3::setExclusiveMode()` sets `linkDirty`, so the blank
frame paints immediately.**Fixed.** Rows 3–4 now follow the live link `setLinkContext()` already pushes:

| Live link | Row 3                    | Row 4        |
| --------- | ------------------------ | ------------ |
| Bluetooth | `Bluetooth : <name>`     | `Type : SPP` |
| WiFi      | `WiFi : <ssid>`          | `IP : <ip>`  |
| Both      | `BT + WiFi connected`    | `IP : <ip>`  |
| None      | idle rotation, unchanged |              |

Keyed on the link, not on `wifiEnabled && btEnabled`, so it survives S-12
(turning the page off on a Bluetooth connect would otherwise make "exclusive"
false and restart the rotation over a dead Wi-Fi link). Idle rotation untouched.

Verified: contract gate 0 failures in both cars; both compile on esp32 4.0.0
(60% flash / 24% RAM). Pushed: 4WD4M `2ff2795`, 2WD1M `2c92bd2`. The gate had no
rule pinned to the old hide-the-rows behaviour, so no rule text needed changing
(the `U-107c` comment is rewritten in place).

## S-02 — Boot shows the car's own hotspot first, then the saved router; stale details

> "the car should remember the setting toggle that is last set by the app or the
> remote … and also the remember the last used router should also work properly
> and the car should remember those things during the boot and display no stale
> things. Currently thought the remmber the last saved router is turned on it
> doesnt show the last save router detail properly and on oled too and for a
> breif time the car shows the defautl cars own hotspot right after the boot and
> then it used to swithc to the last save one when it was workign at previous
> versions build. please fix this and make things load just after on and have no
> stale details displayed there."

**Status:** `DIAGNOSED` (partly) · **Phase 1** · both cars

**Reading.** Three claims: (a) toggles must be restored at boot and honoured;
(b) the last-used router must be restored at boot and shown truthfully on OLED
and in the app; (c) the OLED must not show the own-hotspot fallback during the
boot join window, then flip.

**Evidence.** `WebServerComm::wipeRoutersOnFreshFirmware()` (version change wipes
routers) + `loadStoredWifi()`/`storedSsid_` hold the saved pair; `startOwnAP()`
runs in the STA-down window, so the AP is genuinely up first and the OLED
renders `AP:<name>,<ip>` from `extraInfo` until the STA join resolves. The
"blink to the saved router after a second" is that gap being rendered, not a
stale read.

**Planned fix.**

1. Persist and restore the full settings surface at boot: mode, speed, trim,
   steer limit, `t_wifi`, `t_bt`, `boot_autojoin`, `page_off` (most already
   exist — audit each key has a writer AND a reader).
2. During the boot join window render a transitional frame
   (`WiFi : connecting…` / `IP : --`) instead of the AP fallback, so the AP name
   never appears and then flips. The AP fallback is only shown after the join
   attempt has actually resolved to "AP only".
3. On a fresh-version wipe, show that the routers were cleared (the RUNSHEET
   already expects this) rather than silently showing the own hotspot as if it
   were the last router.

**Open point.** (c) needs the exact boot ordering read in Phase 1 — `setup()`
touches the web layer before `btComm.begin()` on 1.3.11, so the first rendered
frame may precede the NVS load. Confirmed during Phase 1, not guessed here.

## S-04 — Reconnect fails until the car is power-cycled; same method fails after an app restart

> "there is not disconnect button now so i could not check why the app doesnt
> connect again the to another method due to car being busy or it is the bug that
> is not allow the connection second time due to the bug. but it is connecting if
> the car is restarted or after the power cycle. ALso i noted the same method also
> doesnt connects if app closed and reconnected and other functions of the car is
> oka like mode swith switch buttons too."

**Status:** `OPEN` · **Phase 2 (car) + Phase 3 (app)** · **highest severity**

**Reading.** Mode switching over an existing link still works, so the command
path is alive — only NEW link admission is failing. That points at link
teardown/admission state (a latch or a socket the car still believes is
occupied), not at the radio.

**Leading hypothesis.** `admitSecondLink()` latches its verdict until "both links
are up"; if the first link's socket is never reaped, the next connect is refused
with `LINKCAP=0` and never recovers without a reboot. `LINKCAP` is also a live
heap verdict since 1.3.19, so a leak-free but low-heap car reports 0 forever.

**Planned fix (Phase 2).** Reproduce by reading the admission + WS client
bookkeeping, then: release the latch when the incumbent link closes; reap dead
WS clients on a bounded timeout; expose why a connect was refused
(`;LINKCAP=` plus a serial reason) so the app can say it instead of failing
silently.

**Note.** This is the entry most likely to be a real firmware bug, and it must
be fixed before S-03's disconnect button can be validated.

## S-12 — Bluetooth connected ⇒ web page off, and no broadcast IP shown

> "also when bluetoooth is connected the webpage should be off by default and
> there should be no broadcast ip displayed too."

**Status:** `OPEN` · **Phase 1 (car) + Phase 3 (app)** · **CONTRACT CHANGE**

**Reading.** Today the page server is always-on (`page-always-on` rule) and the
broadcast IP is a displayed fact. The owner is asking for the opposite default
while a BT client is connected: page OFF, no broadcast IP.

**Decision taken (stated, not guessed).** Implement it as a **default, not a
lock**: when the first BT client connects, the page server turns OFF and the
broadcast IP is hidden on the app chips and the OLED; the owner can still turn
the page back ON manually, and the choice is not persisted as `page_off` (so
disconnecting BT restores the previous page state). Otherwise the car loses its
web path permanently after one BT connect.

**Risk — explicit.** This contradicts the pinned `page-always-on` rule in
`check-webpage-js.mjs` and `U-113-9/U-113-11` ("both ON ⇒ both offered"). Both
must be rewritten in the same commit, with the owner's ruling recorded, or the
gates will (correctly) go red.

**Two questions I will answer by measurement, not assumption.**

1. **What does the second pad control?** The 2WD1M has exactly one steering axis
   plus throttle, so a second independent pad has no extra axis in this firmware.
   Candidate intents: (a) camera/gimbal pan-tilt — not in this firmware;
   (b) a second simultaneous control (steer on one, throttle on the other).
   I will implement (b) — a split control (left pad = steering, right pad =
   throttle) that produces the same wire frames the single pad produces, so no
   firmware change is needed and the car behaviour is unchanged. If the owner

2. **Does 2WD1M signed drive support split X/Y?** `SPD<n>` + `SERVO<n>` are
   independent frames, so yes: steering can change while throttle holds.

**Planned fix.** App: measure the available width at the narrowest supported
landscape width, size both pads from that measurement, and verify no existing
control clips or wraps (the `U-123-4` 640 px case is the floor). Page: the same
two-pad arrangement, same bindings, landscape only.

## Cross-cutting notes

- **S-01 × S-12:** the OLED's "hide rows when connected" is keyed on both
  transports being enabled. Turning the page off on BT connect (S-12) makes that
  condition false and would restart the idle rotation over a dead Wi-Fi link.
  Both must be fixed together in Phase 1.
- **S-02 × S-11:** a saved steer limit of 90 must be clamped to the new 60 on
  load, or the car keeps a value the UI can no longer express.
- **S-04 before S-03:** a disconnect button is untestable until second-link
  admission recovers without a reboot.
- **Firmware version:** Phase 1 changes firmware behaviour. Any `FW_VERSION`
  bump wipes saved routers (S-02's own risk) — so Phase 1 will state whether it
  bumps, and the RUNSHEET will say what the bench must re-enter.
- **Gates that will need deliberate rule updates:** `page-always-on` and the
  both-transports-offered assertion (S-12), `exclusive`-mode wording (S-01).
