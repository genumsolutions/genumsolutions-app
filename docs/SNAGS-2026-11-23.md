## S-01 — OLED goes blank on the last two rows once a method connects

> "before doing a conection the cars oled shows the both method connection
> details in the last two line which is good. but when and after the car gets
> connected, it should only display about the connected method only and stop
> blinking. But currently show blank on the last two line which should be
> rectified."

**Status:** `FIXED` (device verification pending) · **Phase 1** · both cars

**Reading.** Idle: rows 3–4 alternate Wi-Fi / Bluetooth frames ("blinking") —
correct. Connected: the owner expects ONE static frame for the connected method
only. Actual: both rows are blank.

**Evidence.** `Oled_1_3.cpp` `redrawNow()`:

```cpp
// U-107c: when one connection is active (exclusive mode), hide connection-method
// rows entirely. Only render when both transports are available (idle).
if (!exclusiveMode) { …draw line3/line4… }
```

`ModeManager::pushExclusiveMode()` sets `exclusive = anyConnected && wifiEnabled
&& btEnabled`, so the normal "client connected, both transports on" case hides
the rows by design. `Oled_1_3::setExclusiveMode()` sets `linkDirty`, so the blank
frame paints immediately.**Fixed.** Rows 3–4 now follow the live link `setLinkContext()` already pushes:

| Live link | Row 3                    | Row 4        |
| --------- | ------------------------ | ------------ |
| Bluetooth | `Bluetooth : <name>`     | `Type : SPP` |
| WiFi      | `WiFi : <ssid>`          | `IP : <ip>`  |
| Both      | `BT + WiFi connected`    | `IP : <ip>`  |
| None      | idle rotation, unchanged |              |

Keyed on the link, not on `wifiEnabled && btEnabled`, so it survives S-12
(turning the page off on a Bluetooth connect would otherwise make "exclusive"
false and restart the rotation over a dead Wi-Fi link). Idle rotation untouched.

Verified: contract gate 0 failures in both cars; both compile on esp32 4.0.0
(60% flash / 24% RAM). Pushed: 4WD4M `2ff2795`, 2WD1M `2c92bd2`. The gate had no
rule pinned to the old hide-the-rows behaviour, so no rule text needed changing
(the `U-107c` comment is rewritten in place).

## S-04 — Reconnect fails until the car is power-cycled; same method fails after an app restart

> "there is not disconnect button now so i could not check why the app doesnt
> connect again the to another method due to car being busy or it is the bug that
> is not allow the connection second time due to the bug. but it is connecting if
> the car is restarted or after the power cycle. ALso i noted the same method also
> doesnt connects if app closed and reconnected and other functions of the car is
> oka like mode swith switch buttons too."

**Status:** `FIXED` on the car side (device verification pending) · **Phase 2** ·
**highest severity**

**Reading.** Mode switching over an existing link still works, so the command
path is alive — only NEW link admission is failing. That points at link
teardown/admission state (a latch or a socket the car still believes is
occupied), not at the radio.

**Leading hypothesis.** `admitSecondLink()` latches its verdict until "both links
are up"; if the first link's socket is never reaped, the next connect is refused
with `LINKCAP=0` and never recovers without a reboot. `LINKCAP` is also a live
heap verdict since 1.3.19, so a leak-free but low-heap car reports 0 forever.

**Fixed — the root cause was in the transport-ownership loop, not admission.**
The loop computed:

```cpp
const bool wifiLive =
    webServerComm.apStationCount() > 0 || webServerComm.hasWsClients();
```

and held the U-129 park while true. Android keeps the Wi-Fi association after
the app is closed, so a phone sitting on the car's hotspot with no page open
kept `wifiLive` true. The car then stopped Bluetooth, called
`setOtherLinkParked(true)`, and `linkCapCode()` answered `0` — so the app
declined to offer a link the car said it would park. Nothing cleared the latch,
hence "works after a power cycle". Mode switching kept working because the
command path was never broken.

`wifiLive` is now `hasWsClients()`. The page talks over the port-81 WebSocket,
so that is the real "a page is open" signal; a bare association is not a
controller. Closing the app now drops `wifiLive`, and the 4 s
`LINK_OWNER_HOLD_MS` path — which already existed — re-opens the parked sibling.

Both cars compiled clean and pushed: 4WD4M `adc6e06`, 2WD1M `092b34f`.

**Still owed.** Device proof: Wi-Fi link → close app → connect over Bluetooth
without touching power, then the reverse. Until that runs, this entry stays
un-verified (F-61).

**Note.** This is the entry most likely to be a real firmware bug, and it must
be fixed before S-03's disconnect button can be validated.

## S-09 — Neither car replays last telemetry/settings after a power cycle

> "also both the cars are not remmembering things. they should all the telmetries
> and the the setting things that has been received and set in previous use and
> show on next power cycle."

**Status:** `AUDITED` (car half needs no change) · `OPEN` on the app half · **Phase 1 + 3**

**Reading.** Two halves: (a) car-side persisted settings (mode, speed, trim,
steer, toggles, router) must be restored and reported on the first STATE after
boot; (b) "telemetry" shown on next launch is app-side memory per device (the car
persists no live telemetry). Both must be labelled as "last known, not live"
rather than passed off as current — the app already has that affordance
(`U-128-2` row).

**Audit (Phase 1).** Every persisted key, its writer, its reader, and the wire
field that publishes the restored value — both cars:

| Key                             | Car   | Written by                       | Read at boot by                | Published as        |
| ------------------------------- | ----- | -------------------------------- | ------------------------------ | ------------------- |
| `mode`                          | both  | `saveBootState()` (1 s debounce) | `applyBootState()`             | `STATE;MODE=`       |
| `spd`                           | both  | `saveBootState()` (1 s debounce) | `applyBootState()`             | `STATE;SPD=`        |
| `trim`                          | 2WD1M | `saveDriveTrim()`                | `applyBootState()`             | `STATE;TRIM=`       |
| `steerlimit`                    | 2WD1M | `saveSteerLimit()`               | `applyBootState()`             | `STATE;STEER=`      |
| `t_wifi`                        | both  | `WIFICFG;WIFI`                   | `loadStoredWifi()`             | `STATE`, `/status`  |
| `t_bt`                          | both  | `WIFICFG;BT`                     | `loadStoredWifi()`             | `STATE`, `/status`  |
| `boot_autojoin`                 | both  | `WIFICFG;AUTOJOIN`               | `loadStoredWifi()`             | `STATE`, `/status`  |
| `page_off`                      | both  | `WIFICFG;WIFI;PAGE`              | `loadStoredWifi()`             | `;PAGE=`, `page_on` |
| `wifi_ssid` / `wifi_pass`       | both  | `WIFICFG`, router list           | `loadStoredWifi()`             | `ssid`, `networks`  |
| `last_ok_ssid` / `last_ok_pass` | both  | last successful join             | `loadStoredWifi()`             | `want`              |
| `fw_mark`                       | both  | boot                             | `wipeRoutersOnFreshFirmware()` | — (local)           |
| `config_epoch`                  | both  | `stampConfigWrite()`             | **nothing**                    | —                   |

So the car half is **already complete**: every setting the owner can name is
persisted, restored before any radio is raised, and published on the 1 s `STATE`
tick — not only when a client happens to ask, so a reconnecting app receives the
restored values within a second without a `REQ_STATE`. (`config_epoch` is
write-only; it is a harness stamp for the mutate gates, not a setting, and is
left alone rather than "fixed" into a reader nobody needs.)

Two limits worth stating rather than hiding:

- The mode/speed write is debounced 1 s, so a change followed by a power cut
  inside that second is lost. Deliberate: an NVS write per keypress would wear
  the flash.
- The car persists **no live telemetry** (battery, RSSI, uptime are readings, not
  settings). "Show the telemetries on next launch" therefore cannot be a
  car-side restore — it has to be the app remembering what it last received, per
  device, and labelling it as last-known.

**Remaining work is app-side (Phase 3).** Restore per-device last-known settings
_and_ last-known telemetry on open, through the existing "last known, not live"
row, and let the first `STATE` tick replace it silently. No firmware change.

## S-12 — Bluetooth connected ⇒ web page off, and no broadcast IP shown

> "also when bluetoooth is connected the webpage should be off by default and
> there should be no broadcast ip displayed too."

**Status:** `FIXED` (car half; device verification pending) · **Phase 1 (car) + Phase 3 (app)**

**Reading.** The owner wants: while a BT client is connected, the page server is
OFF by default and no broadcast IP is shown.

**What the code actually did — and the correction to this entry's first guess.**
The physical behaviour the owner asked for **already existed**: when both
transports are enabled and Bluetooth takes the link, the sketch calls
`webServerComm.suspendAP()`, which stops `server`, closes the WebSocket, stops
mDNS and drops the beacon; `resumeAP()` puts all of it back after the disconnect
(`LINK_OWNER_HOLD_MS`). The AP-derived IP fields (`apIp`, `bcastIp`,
`subnetMask`, and the `ip` fallback) are gated on `apRunning_`, so they are
already empty in that state. This entry originally predicted a **contract
change** against `page-always-on` — that prediction was wrong, and no rule
needed rewriting: the park is not a client gate on the serve path, which is what
`page-always-on` actually pins.

**The real defect was the report.** Both published answers named the _setting_
instead of the _serve state_: `pageServerIsOn()` returned `!pageOff_`, and
`/status` recomputed `(pageOff_ || !wifiEnabled_) ? 0 : 1`. While BT owned the
link they therefore said ON for a page that nothing was answering — which is
exactly how "the webpage is still on over Bluetooth" reads from the app, and why
the owner asked for it to be off by default.

**Fixed.** `pageServerIsOn()` is now `!pageOff_ && !apSuspended_` — the serve
truth — and `/status` reads that same accessor instead of restating the
condition, so `;PAGE=` and `page_on` cannot disagree. `pageOff_` still holds the
owner's choice, so the page returns on its own after the BT disconnect and a
persisted OFF is still honoured. Both cars compiled clean (60% flash / 24% RAM),
contract 0 failures, webpage-js PASS. Pushed: 4WD4M `9f67fbc`, 2WD1M `88b8e9f`.

**App half (Phase 3, with S-10).** The toggle must now render this honestly: when
`link_owner:"bt"` and `page_on:0`, show the page as off _because Bluetooth owns
the link_ and do not offer a flip that cannot take effect until the disconnect —
otherwise the owner presses ON, the car answers OFF again, and a truthful report
reads as a broken switch. `link_owner` is already on the wire for this.

## Cross-cutting notes

- **S-01 × S-12:** the OLED's "hide rows when connected" is keyed on both
  transports being enabled. Turning the page off on BT connect (S-12) makes that
  condition false and would restart the idle rotation over a dead Wi-Fi link.
  Both must be fixed together in Phase 1.
- **S-02 × S-11:** a saved steer limit of 90 must be clamped to the new 60 on
  load, or the car keeps a value the UI can no longer express.
- **S-04 before S-03:** a disconnect button is untestable until second-link
  admission recovers without a reboot.
- **Firmware version:** Phase 1 changes firmware behaviour. Any `FW_VERSION`
  bump wipes saved routers (S-02's own risk) — so Phase 1 will state whether it
  bumps, and the RUNSHEET will say what the bench must re-enter.
- **Gates that needed updates:** none so far. S-01's `exclusive`-mode wording was
  rewritten in place with no rule pinned to it, and S-12 turned out not to
  contradict `page-always-on` at all — the BT park already existed and only its
  report was wrong, so the rule was left alone.
